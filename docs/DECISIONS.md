# Project ASTRA decisions

## ADR-037 — Project authority is minted only over a directory that did not exist (Implemented, 2026-10-15)

Karl asked Astra to build a whole project from one sentence and approve it once, without weakening CA-01 or CA-01B. The authority is therefore a separate mechanism with one load-bearing property: it can only be granted over a directory proven absent at plan time and created by that task. That makes it structurally impossible for a one-sentence project request to reach a repository Karl already has, which is the only way "approve once, write many files" can be safe. Every write re-proves containment through the existing `pathGuard`, refuses secrets and dependency directories, rejects links, and consumes a written budget; deletion, dependency installation, network access, credentials and anything outside the project are never in scope and each is refused with its reason rather than silently skipped. The project scope is part of the approval fingerprint, so widening it after approval invalidates the approval exactly as widening a patch scope always has.

The build writes a deterministic, dependency-free baseline **first** and validates it, so a working project is the floor; the local coding model may then improve application files, restricted to the approved manifest and re-validated on disk. On failure the loop repairs within scope under a short explicit budget, and if that fails it reverts model-written files to the verified baseline and validates again. Rationale: the acceptance criterion is a *working* website, and "generate it with a model" and "guarantee it works" are different claims. Layering them this way means the model is used where it adds value and cannot destroy the floor. The first validation pass always runs to completion even if the time budget is spent, because a report with no result is worse than a report that states what failed. A dependency-free default was chosen over a React/Vite stack because dependency installation remains blocked pending separate authorisation, and a scaffold that cannot be installed is not a scaffold Karl can launch.

## ADR-036 — Names are folded, not loosened; a recursive delete shows everything (Implemented, 2026-10-15)

Karl authorised Astra to create and remove files, which CA-01B already covered, and chose two things explicitly for directories. First, a directory delete is **fully recursive with a full file listing**: every path and size is printed in the plan, `.git` is called out when present, and a directory beyond 5000 entries is refused rather than truncated. Approval plus complete disclosure is the whole guard, because the operation is irreversible and any weaker rule would hide scope. Second, names are **folded rather than loosened**: "Astra's Blog" becomes `AstrasBlog`. Folding was chosen over widening the safe-name rule because the output alphabet stays letters-and-digits, so every existing defence — no separators, no traversal, no Windows device name, length bound, start-with-a-letter, containment in `C:\Users\karlr\repos` — survives unchanged. Traversal is neutralised rather than trusted (`../../etc` folds to `Etc`), and an exact device name is still refused. Rationale: widening the regex to permit spaces and apostrophes would have required re-deriving every path-safety property, whereas folding needs no new property at all. Two corrections came out of the same investigation: `folder`/`directory` were removed from the repository-creation nouns, because they had begun routing "create a folder" into the project scaffolder; and the spoken-name extractor stopped at the first apostrophe, which silently truncated "Astra's Blog" to "Astra". A recursive delete also adopts the staleness guarantee a file delete already had: the directory manifest is hashed when planned and re-read immediately before removal, so a folder that changed after Karl read the listing is refused rather than deleted.

## ADR-035 — Machine-state claims require a tool result, and routing may not fall through (Implemented, 2026-10-15)

Astra's false claim that `C:\repos\Astra's Blog` existed was caused by routing, not by weak prompting. The fix is therefore structural rather than advisory. First: no message naming a loopback address, a Windows path or a project-existence claim may reach the chat model; `routeCodingIntent` ends in a safety net that routes those to `check_path`, `check_repository` or `check_service`, so `chitchat` is unreachable for them regardless of phrasing. This is preferred over extending the rule word list, because the defect *was* an unenumerated phrasing and enumeration cannot prevent the next one. Second: existence, Git identity and service availability may be asserted only from a real syscall or socket result in `workspace/verification.ts`, and `isGitRepository` is true only for a real `.git` entry — never from a name or from the presence of source files. Third: verification stays read-only, resolves paths through the existing `pathGuard` containment check, and probes loopback addresses only, so a new capability was needed to make claims honest without adding authority. Fourth: nothing here is a canned refusal. Every branch performs a real check whose result becomes the reply, and an unavailable capability is stated together with the action that would resolve it, so Astra is not being trained to decline. Rationale: CA-01B already proved that a trusted tool result outranks generated prose for files; the same argument applies to directories, repositories, services and memory, and the enforcement point is the router rather than the prompt.

## ADR-034 — Qwen may draft a file, but CA-01 alone may write it (Implementation under acceptance, 2026-10-15)

Karl authorised CA-01B to remove the requirement for user-supplied fenced code. Deterministic chat routing resolves a file target inside the configured root before model inference. The installed local coding model receives a bounded objective and relevant existing file context as untrusted data, returning only candidate content. `CodingBridge` validates a fresh `DirectFilePlan` and submits the complete content to the existing CA-01 approval engine. The model never supplies an approval, execution result or destination outside the trusted resolver. A create request targeting an existing file is refused; Karl must explicitly request an edit or replacement. This preserves the original direct-file hash check and disk readback while allowing Astra to author proposals. Native UI approval remains a separate owner decision.

## ADR-033 — Approved direct files use exact plans and disk verification (Implemented, 2026-10-15)

Ordinary chat file requests are classified before Gemma, then handled by the existing main-process CA-01 task and approval path. Read is bounded and read-only; create, replace, edit and delete require an absolute path under the configured repository root and a separate reviewed plan. The plan includes the target, action, full new content where applicable, and the current file hash. Execution checks that hash again and verifies the resulting bytes or absence on disk before reporting completion. Creation can make a missing parent directory under that root but never starts Git. The older renderer-supplied `writes` argument is rejected because its contents were not in the approved plan. The model may describe a proposal, but cannot authorise a file mutation or confirm one without a verified task result.

## ADR-032 — Runtime memory authority and bounded citation relevance (Implemented, 2026-10-15)

Astra's own memory capability is answered from a successful read of the trusted personal-memory service before model or research routing; availability is never inferred from an empty record list or a website. Ordinary prompts include the same runtime capability and prohibit generated mutation claims. Knowledge FTS5 remains a recall mechanism, but topic overlap is required before passages are injected, and citation markers are retained only when the answer sentence overlaps the selected passage. This is deliberately a bounded lexical guard, not a claim of semantic proof. The existing SQLite memory database and command authority remain unchanged.

## ADR-028 — Personal Memory V1 extends the existing memory table (Implemented, 2026-10-14)

Karl authorised persistent personal memory on 2026-10-14. Memory is **retrieval of what Karl explicitly said**, not training: Gemma's weights are never changed, and the interface says so. Migration 3 extends the existing `memory` table with `subject`, `status`, `origin`, `sensitivity`, `conversation_ref`, `forgotten_at` and `superseded_reason`, and adds `memory_events` plus `settings`, rather than creating a second, incompatible store. `active` stays authoritative for retrieval so existing queries keep working, and `status` is written with it. ## ADR-029 — The model may suggest a memory but never writes one (Implemented, 2026-10-14)

Memory commands are parsed by a deterministic, pure parser over the text Karl typed, then validated and executed by a trusted service in main before the coding tools and before Ollama. Replies for save, recall, update and forget are built from real rows, so Astra cannot claim a memory that does not exist. When a stable first-person preference is noticed, it is surfaced as a suggestion chip that stores nothing until Karl accepts it, and the whole mechanism can be switched off. Rationale: the same class of failure CA-01 exists to prevent — treating generated text as authority — applies to memory, and "Astra remembered that" is exactly the claim that must never be guessed.

## ADR-030 — Forgetting clears the text and is auditable (Implemented, 2026-10-14)

Forgetting sets `active = 0`, marks `status = 'forgotten'`, records `forgotten_at`, writes a `memory_events` row and **empties the statement text**, so a forgotten memory cannot be injected into a later prompt and is not merely hidden. Corrections keep the old value in `corrections` with the new one, and superseding records point at their replacement. Rationale: Karl must be able to remove information for real; the audit trail stays so a mistaken removal is explainable, and the documentation states plainly that a backup taken before the removal can still hold the old value until it ages out.

## ADR-027 — LW-03 verification harness measures real behaviour (Implemented, 2026-10-14)

The native LW-03 acceptance scripts assert on the renderer's own state and must fail when the product misbehaves, so a check is never loosened just to make a run green. Three harness defects were corrected this session: a 10 s chat-approval wait that could expire while local inference and the 30 fps world shared the machine, a Centre assertion that required `state === 'idle'` when the idle scheduler legitimately keeps her `interacting`, and a 12 s desk-work deadline that did not cover a walk across the room plus sitting down. A CDP sampling guard on movement now bounds ground speed against the real sample gap instead of a fixed allowance, an occluded or minimised window counts as the required render pause rather than a crash, and disposable profile cleanup retries and then warns instead of failing a passing run. Where a real limitation cannot be asserted either way — a learning fetch on this machine indexes in about 3 s while the walk to her chair takes about 7 s, so seated desk work during learning was never observed — the harness records an explicit observation in `test-results/lw03/observations.json` and `docs/LW_03.md` keeps the milestone PARTIAL, rather than converting the gap into a pass or hiding it.

## ADR-015 — LW-02A measured scene scheduling (Implemented, 2026-10-13)

Replace LW-01's 12 fps `setTimeout` render cap with a 30 fps cap paced by `requestAnimationFrame` while the scene is visible. The ~10.9 fps LW-01 concurrent-chat result was consistent with its deliberate 12 fps cap: a controlled replay of that cap measured 10.75 fps during generation, while `renderer.render` used about 0.4 ms CPU per frame. A 30 fps candidate on the same scene held about 30 fps during Gemma generation in brief controlled samples. Retain stop/cancel behavior on hidden/minimised, offscreen, manual pause and reduced-motion state, and one resize draw. Store a bounded renderer-local frame sample buffer for read-only diagnostics; it contains timings and draw counts, not conversation text. Renderer timing is CPU wall time, not a GPU timer. Whole-device `nvidia-smi` readings cannot establish per-scene VRAM use. Do not infer sustained 30 fps from these short samples. Update ADR-013's historical 12 fps target accordingly.

**LW-02A amendment (2026-10-13):** the reduced-motion decision must read `matchMedia('(prefers-reduced-motion: reduce)')` freshly each time the state is evaluated rather than caching a `MediaQueryList`. A cached list was observed to keep reporting `matches === false` while a fresh query reported `reduce`, so the scene kept rendering under an emulated reduce preference and the state label never changed. The `change` listener is retained as a best-effort trigger and a 300 ms watchdog re-synchronizes state so a stopped scene resumes when the preference is cleared. The cost is one media query evaluation per frame plus a cheap interval.

## ADR-020 — Intelligence V1 storage: Node's bundled SQLite (Implemented, 2026-10-13)

Use the SQLite build shipped with Node (`node:sqlite`) rather than adding a native dependency such as `better-sqlite3`. Rationale: Astra is local-first and offline-capable, and a compiled native module adds an install step, a rebuild surface on every Electron upgrade and a supply-chain dependency for no functional gain — `node:sqlite` exposes the same synchronous API, FTS5 is available, and it is verified working on the Node 24.21 bundled with Electron 44. The cost is that Node marks the module **experimental**, so the API could change between majors; this is recorded as a known risk rather than hidden. The database lives in Electron's user-data directory, never in the tracked source tree, consistent with ADR-003. Migrations are append-only and idempotent; a corrupt file is quarantined beside the original before replacement, and backup uses `VACUUM INTO` so a copy is consistent under WAL. No migration may define a credential column, which a test enforces.

## ADR-021 — Intelligence V1 network trust boundary (Implemented, 2026-10-13)

All outbound HTTP lives in one module, `src/main/research/reader.ts`, and every URL must first pass `urlGuard.assertFetchAllowed`. A URL is admitted only if it is HTTPS, carries no credentials, uses port 443, matches the approved host **exactly** (not a suffix, subdomain or registrable domain), stays inside the approved path prefix, and **every** DNS answer is a public address. Loopback, RFC1918 private, link-local (which also covers `169.254.169.254` metadata), CGNAT, multicast, reserved, IPv6 loopback/ULA/link-local and IPv4-mapped, NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) spellings are all refused. The validated address is then **pinned**: the socket connects to that literal IP with the TLS `servername` still set to the real hostname, which is what closes DNS rebinding. Every redirect hop is re-validated from scratch and a hostile target is never requested. Links found on a page pass through the same function, so a page cannot widen a crawl. Rationale: host allowlisting alone is not a boundary, because a hostile or compromised page controls its own links, redirects and DNS. `robots.txt` is validated against the same origin with the path prefix relaxed to `/`, because it necessarily lives outside an approved path — that relaxation is used for nothing else.

## ADR-022 — Intelligence V1 privilege levels (Implemented, 2026-10-13)

Privileged actions are grouped into four levels, and the boundary between them is **scope**, not intent. `read_only` covers repository discovery, listing, approved reading and knowledge search. `task_approval` covers creating repositories, editing source, creating branches and running commands. `separate_approval` covers commits, pushes, remote creation, deletion, destructive migrations and network uploads. `forbidden` covers credential access, disabling protections, acting on website content, writing outside the root, self-granting permission and destructive system operations. `ApprovalManager.assertApproved(action, scope)` runs immediately before the operation, not when the plan was made, and requires an approved record whose scope covers the request. Scope matching is a **ceiling, not a floor**: every key in the approval must be present and equal, so an approval for `src/a.ts` cannot authorise `src/b.ts`. Rationale: "approved" without a bound scope drifts into standing permission, which is the failure mode this milestone is most exposed to. `FORBIDDEN_ACTIONS` can never be approved at any level.

## ADR-023 — Intelligence V1 repository edits are repository-scoped (Implemented, 2026-10-13)

File writes are validated against the **repository** root, not merely the approved workspace root. A test found the gap: from inside a project, `../escaped.js` resolved inside `C:\Users\karlr\repos` and was therefore accepted, writing outside the project into its parent. `repoScope()` in `fileTools.ts` narrows the sandbox to the target repository for every mutation. Rationale: Karl's approved root contains sixteen unrelated real projects; being inside the root must never imply permission to edit a sibling. Containment also canonicalises paths, resolves symlinks and Windows junctions, walks up to the nearest existing ancestor so a not-yet-created file cannot escape through a linked parent, compares case-insensitively, strips trailing dots and spaces, and refuses NUL bytes and reserved device names.

## ADR-024 — Intelligence V1 coding delegation requires measured reliability (Implemented, 2026-10-13)

Coding work is delegated to `qwen2.5-coder:7b` only when a measured reliability reaches `MIN_CODING_RELIABILITY = 0.6`; **unmeasured means not trusted**, so the router refuses by default. Gemma `gemma3:4b` remains the conversational model. The benchmark (`scripts/benchmark-coding-model.mjs`) scores short, single-shot, objectively checkable tasks rather than asking a model to rate itself. The measured result on 2026-10-13 was **0.83 (5 of 6)**, with test interpretation failing. That score is explicitly **not** treated as evidence of reliable unattended multi-step development: six short cases can detect a broken model but cannot certify a good one, so delegated work stays bounded behind approval, is verified by running tests, and never commits or pushes without separate approval. Rationale: the earlier M1 benchmark did not establish reliable TypeScript coding, and the milestone instruction is explicit that a weak coding result must be documented rather than worked around. The failing case is recorded rather than discarded.

## ADR-025 — Retrieved web content is data, never authority (Implemented, 2026-10-13)

Web content and model output can never grant permission, trigger a command or edit a file. Concretely: `MemoryStore.remember` throws for `origin === 'web'`, so nothing scraped becomes a trusted memory; retrieved passages are wrapped in labelled `<passage>` tags under a header marking them untrusted data, and the warning precedes the payload; the system prompt instructs the model to ignore any request, command or permission claim inside a passage; and `FORBIDDEN_ACTIONS` includes `command.from_web_content`. Rationale: prompt injection is the expected case, not the exceptional one, when fetching pages from the public internet. Prompt-level defences are necessary but not sufficient, so the structural defences (memory rejection, approval allowlists and the absence of any model-driven command construction) are what actually carry the guarantee.

## ADR-019 — LW-02B-R1 sculpted-head construction and validation (Proposed, 2026-10-13)

Adopt **displacement of a shared skull landmark table** as the way the character's face is constructed, instead of placing separate primitive features on a smooth head. `SKULL`, `FACE` and `facial_displacement` in `scripts/blender/create_astra_character_r1.py` push eye sockets, brow ridge, nose, lips, cheekbones, jaw and chin into one continuous head mesh, and dependent geometry is positioned through `face_surface_y(x, z, expression)` so it always lands on the actual sculpted surface. Rationale: LW-02B's procedural look was caused by floating feature primitives, not by shading or polygon count, so style passes could not fix it. Eyes are spherical objects seated in the sculpted sockets with lids lofted along the aperture; iris, pupil and glint must sit **proud** of the eyeball surface, and lip volume must straddle the seam, or both defects are invisible until a render is inspected. Expressions are expressed as displacement parameter sets (currently `neutral` and `smile`), **not** as shape keys, because shape keys are part of the unapproved rig work. The script performs a static integrity validation (object names, transforms, materials, degenerate faces, duplicate vertices, inward-facing normals) and reports it; this is explicitly **not** an interpenetration or skinning test. 40,232 triangles is reported honestly as exceeding the ≤ 30,000 production budget, which applies to a future retopologised asset. No application code, asset loader, armature, skin weights, morph targets, clips or GLB exist, and Karl has not approved the design.

## ADR-018 — LW-02B refined design scale and asset boundary (Proposed, 2026-10-13)

Adopt a **1.70 m, 5.76-heads-tall** stylised young-adult proportion for the character design instead of the LW-02A blockout's ~3.5 heads. Six heads was the brief; 5.76 is chosen because a literal 6.0 with the same shoulder width reads leggy and toy-like, while anything below ~5.5 drifts toward stylised chibi again. The figure is authored in metres with the feet on z = 0, facing -Y, up +Z, her left side +X, and a shared landmark table so facial features sit on the skull surface rather than being placed by eye. Character design generation stays in Blender scripts under `scripts/blender/` and remains **outside** the application: LW-02B changed no renderer, main or preload code, added no asset loader and no remote fetch, and the labelled procedural mannequin remains the runtime fallback. The refined blockout is a design proposal **awaiting Karl's approval**, not approved art, a rig or a production asset; its 32,588 triangles are a blockout measurement and not a claim against the ≤ 30,000 production budget. The LW-02A blockout script and renders are preserved unchanged as the "before" record. Production retopology, skinning, morph targets, clips, GLB export and application integration all require separate LW-02C authorization after Karl approves the design.

## ADR-017 — Future intention validation boundary (Proposed, 2026-10-13)

If approved later, the conversation engine may propose a small typed high-level intent such as `walk_to_desk`, `sit`, `wave` or `read_book`; it must not produce an executable renderer/OS command. A separate animation/world controller must allowlist intent names and target IDs, validate preconditions, permissions, location, reachable path, object state and resource budget, then execute or refuse with cancellation and safe fallback. Website text, model output and journal records remain untrusted data and cannot authorize a new intent, alter the allowlist or issue desktop instructions. External read-only research keeps ADR-014's domain/DNS/redirect/local-network limits and requires Karl's explicit approval. This is only a boundary design in LW-02A; no autonomous controller, browsing or learning has been implemented.
